# Name Generator → Sales Analytics

This is a **portfolio project** demonstrating an end-to-end analytics
engineering workflow: synthetic data generation with Python/Faker, append-only
raw data loaded into Neon Postgres, dbt staging/mart models, automated tests,
and a daily-scheduled orchestration job.

## Data flow

1. `scripts/generate_names.py` generates fake customer records with unique
   UUIDs and writes a batch to `data/incoming/raw_names.csv`.
2. `scripts/generate_sales_transactions.py` generates a matching batch that
   references those customers and the static product catalog.
3. `scripts/load_to_neon.py` appends both generated batches to the `raw`
   schema in Neon. Batch dates and row numbers make retries idempotent.
4. `dbt seed --select raw_products` loads the small, version-controlled
   product catalog as reference data.
5. Staging models clean and type the Neon sources and product seed.
6. Mart models join and aggregate the staging layer into business-facing
   tables: `customer_sales` (row-level join) and `customer_sales_summary`
   (per-customer lifetime value).

## Where to look

- **Staging models** — see the `staging` folder for cleaned views over the
  Neon sources and product seed.
- **Mart models** — see the `marts` folder for the customer/sales join and
  aggregate tables used for analysis.

All data is synthetically generated — no real personal information is used
anywhere in this project.

{% docs user_id %}
Stable, globally unique customer identifier (UUID), generated once per
customer in `scripts/generate_names.py` and reused as the foreign key on
every sales transaction. This is the join key between the customer
("names") data and the sales_transactions data.
{% enddocs %}

{% docs name_id %}
Database-generated integer surrogate key for a customer row. Use `user_id`
for stable customer joins instead.
{% enddocs %}

{% docs transaction_id %}
Sequential integer primary key identifying a single sales transaction line.
{% enddocs %}

{% docs product_id %}
Integer primary key identifying a stock item in the product catalog
(`scripts/generate_products.py`). Used as the foreign key on every sales
transaction so product name/category/price are stored once rather than
repeated on each transaction row.
{% enddocs %}

{% docs full_name %}
Customer's full name, generated by concatenating a random first and last
name (`first_name` + " " + `last_name`) via Faker.
{% enddocs %}

{% docs email %}
Customer's email address. Generated as a unique, fake value via Faker — not
a real, deliverable address.
{% enddocs %}

{% docs age %}
Customer's current age, computed as the number of full years between
`birthdate` and the current date at model build time. Will change on
re-runs as time passes, even without regenerating the underlying data.
{% enddocs %}

{% docs total_amount %}
Total value of a single sales transaction line, calculated as
`unit_price * quantity` at the time the synthetic data was generated.
{% enddocs %}

{% docs lifetime_value %}
Sum of `total_amount` across every sales transaction linked to a customer's
`user_id`. The core "how much has this customer spent" metric used in the
`customer_sales_summary` mart.
{% enddocs %}

{% docs region %}
Synthetic sales region assigned to each transaction (e.g. "North America",
"Asia Pacific"). Not derived from the customer's actual address — it is an
independently randomized field on the transaction, mirroring how a
multi-region retailer like Wide World Importers might record the fulfilling
sales region.
{% enddocs %}
